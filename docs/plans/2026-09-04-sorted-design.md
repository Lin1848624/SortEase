## 1. 背景与需求

本机为 Forge 1.20.1 整合环境，且装有大堆叠相关模组（如 Bigger Stacks，堆叠数可被调至
百万乃至 `Integer.MAX_VALUE` 量级，用户常用 `1,073,741,823`）。常见"一键整理"模组多为硬编码
`64 / 16` 槽位上限，在本环境下会错误合并/丢堆叠，或对带"特殊区域"的第三方容器（如
**Create: Storage** 的储物盒/背包、**精妙背包 Sophisticated Backpacks** 的升级槽/过滤槽等）
造成误操作。

用户四项核心需求：

1. **堆叠数量动态化**：整理逻辑不得硬编码堆叠上限，必须按当前物品/槽位实际允许的最大堆叠数实时计算。
2. **特殊区域识别**：能识别界面中的"特殊区域"（如 Create: Storage、精妙背包的升级槽等），**默认不操作**它们。
3. **直观分类界面 + 快捷键**：能在游戏内直接看到每个槽位的分类归属，并一键切换槽位分类类型；键位可自定义。
4. **性能与兼容性**：不卡顿、不产生离谱 bug，与现有模组（Bigger Stacks、Create: Storage、精妙背包等）兼容。

### 范围外（v1 明确不做）

- 不做跨容器自动搬运（如抽屉/终端网络整理）。
- 不做基于条件的复杂整理（按正则/黑名单挑物品等）。
- 不做服务端 GUI 同步 / 非玩家容器的后台整理。

## 2. 总体架构

### 2.1 关键选型：服务端权威执行（推荐），而非纯客户端模拟点击

1.20.1 的容器点击包带 `stateId` 反作弊校验，客户端连续模拟点击极易被判过期而丢操作/不同步，
且第三方槽位限制只有服务端才权威。因此：

- **两端都安装本模组**（单机/自带整合 = 集成服务器自动满足）；
- 客户端按键 → 发送自定义请求包 `SortRequestC2S`（Forge `SimpleChannel`）：
  `{ 容器 containerId, 排序模式, 逐槽覆写表 }`；
- 服务端在自己的菜单（`ServerPlayer.containerMenu`）上**用权威规则执行整理引擎**，
  通过真实容器方法读写（受槽位过滤、锁定、`canPlace/canTake`、物品处理器返回等约束），
  完成后走原版槽位广播同步回客户端；
- 服务端回 `SortAckS2C`（成功 / 无需整理 / 中止原因），客户端以 ActionBar/提示反馈。

> 备注：服务端未装本模组时按键给出明确提示（"服务端未安装 Sorted"），不做降级模拟点击。

### 2.2 客户端组成

- 监听 `RegisterKeyMappingsEvent` 注册键位（`KeyMapping` + `KeyConflictContext.GUI`）。
- 监听 `ScreenEvent.Init.Post` 在打开容器界面时生成"分类快照"。
- 监听 `ScreenEvent.Render.Post` 绘制**槽位分类覆盖层**（颜色边框/角标 + 说明面板）。
- 监听 `ScreenEvent.MouseButtonPressed / KeyPressed` 处理覆盖层交互（点槽位切分类等），
  命中时 **cancel 事件**，避免误把底层容器的物品点动。
- 一个**配置界面 Screen**（供在覆盖层点按钮/Mods 列表进入）。
- 一个小型 Mixin **Accessor**（`AbstractContainerScreen`）仅暴露 `leftPos/topPos` 等受保护字段
  用于把 `slot.x/y` 换算成屏幕坐标——这是本设计唯一用到 Mixin 的地方。

### 2.3 服务端组成

- `SortRequestC2S` 处理器：校验 `containerId` 与玩家当前打开的菜单一致、且菜单可排序。
- **Slot 分类器**（与客户端同一套代码，保证两边分类一致）。
- **整理引擎**（见 §6）：合并 + 排序两阶段；tick 预算分片执行；可随时取消。
- 数据安全：所有写操作经由 Slot/物品处理器真实 API（`mayPlace/canTake/insertItem/extractItem`），
  绝不越权 `set` 未经校验的堆叠；目标槽 `mayPlace` 不通过就换槽。

## 3. 需求 1：动态堆叠数量（不硬编码）

### 3.1 容量判定模型（运行期实时求值）

对"把 X 个物品放入槽 S"这一原子操作，允许的最大量一律动态计算，禁止写死 64/16：

```
cap 判断优先级：
1. 槽级上限：槽位实际封装对象的容量（如 ItemStackHandler.getSlotLimit / Slot 容器上限，
   由 SortedSlotEngine 运行期探测当前菜单实际槽类型得出）；
2. 物品级上限：该物品当前 getMaxStackSize()（Bigger Stacks 等模组补丁后的真实值）；
3. 若 S 非空且与待放入物品同类，还需受 S 已装物品剩余空间约束。

最终可放入量 = min(上述各项)  ，中间量一律用 long 计算再 clamp 到 int，防溢出。
```

- 空槽可容纳多少：按"待放入物品的当前最大堆叠"与槽级上限取小——**在整理当刻读取，而非常量**。
- `Integer.MAX_VALUE` 附近：`a+b` 用 `long` 求和，超界则封顶到 `Integer.MAX_VALUE`（或用户配置的安全上限）。
- 整理对象是"当前打开的容器里的全部参与槽位快照"，而非假设固定的玩家背包布局。

### 3.2 合并键（Merge Key）

只有 `物品相同 && NBT 完全相同`（损坏耐久/附魔等视为不同）才允许合并，避免把不同附魔的工具乱并。
键 = `RegistryName(item) + 完整 NBT`。排序分组键与合并键分开：分组可用"物品 ID / 模组 / 名称"，
合并仅作用于同键。

## 4. 需求 2：特殊区域识别（三层防御）

每个槽位最终归类 = **手动覆写(最高) > 内置预设 > 通用启发式(兜底)**。

### 4.1 槽位分类模型

每个槽位被标为如下「分组 + 参与状态」之一（覆盖层里用颜色/边框区分）：

| 分类                                                    | 默认参与整理 | 说明                                     |
| ------------------------------------------------------- | ------------ | ---------------------------------------- |
| `MAIN`（容器主体）                                      | ✅           | 如箱子主体、背包主存储                   |
| `PLAYER_MAIN` / `PLAYER_HOTBAR`（玩家栏）               | ✅           | 可视配置决定是否包含                     |
| `SPECIAL`（升级槽/过滤槽/护甲/副手/合成/结果/锁定槽等） | ❌           | 默认永不操作                             |
| `UNKNOWN`                                               | 见 4.3       | 启发式未能归类，默认按"可参与但高亮提示" |

允许的分类切换（需求 3 的"一键切换分类类型"）：

- **自动**（跟随规则）→ **忽略**（永不参与）→ **强制参与** 三态循环；右键该槽复位为"自动"。

### 4.2 内置预设（按菜单/容器识别，默认启用，可在配置里逐条开关）

- **原版**：箱子/潜影盒/漏斗/马匹/村民/合成台等菜单 → 结果槽、合成区、护甲、副手、附魔材料槽自动忽略；
  玩家物品栏按 Inventory 内 `getContainerSlot()` 区间自动拆出主栏(9-35)/快捷栏(0-8)/护甲(36-39)/副手(40)。
- **精妙背包（sophisticatedbackpacks）**：背包菜单 → **升级槽区**默认 SPECIAL；其主存储为 MAIN；
  其余 UI 自带特殊行（如有）按反编译结果录入预设。
- **Create: Storage**：储物盒（过滤槽区）、背包的**升级槽区**与**工具存储分格**等按反编译结果录入预设。
- 预设以 **菜单类名/容器类名 + 槽位区间/容器对象** 为键，与具体槽位 GUI 坐标解耦。

### 4.3 通用启发式（未命中预设时兜底）

- 按 `Slot` 封装/所属 `container`（容器对象）划分"连续区段"，同一容器对象视为一组；
- `ResultContainer / CraftingContainer / 玩家 Inventory 的护甲副手段` → 自动 SPECIAL；
- 独立且槽数 ≤ 2 的小容器对象（典型过滤/升级结构）→ 提示为潜在 SPECIAL（覆盖层显示成灰色，但仍允许一键改为参与）；
- 触发"保护槽"的已知标记（Forge `Slot` 无法取出/不允许放入的伪装槽等）在服务端用
  `mayPlace/canTake` 实测判断，作为**引擎层最后的硬保护**（无论分类如何都不会越权）。

> 预设键值与启发式规则的准确性以**实现阶段反编译玩家实际安装的 jar** 为准锁定
> （本机已有 `cfr.jar` 与反编译工作流）。规则只写行为语义，不硬编码堆叠数。

## 5. 需求 3：直观分类界面与快捷键

### 5.1 槽位分类覆盖层（Classification Overlay）

- 进入方式：按「分类视图」快捷键（默认 `P`）在**当前打开的容器界面**上开启；
- 显示：给每个槽位画 1~2px 彩色描边 + 左上角小色点（颜色见 4.1 表；SPECIAL 为红/灰、MAIN 为绿、玩家栏为蓝）；
  底部/角落渲染一行图例说明 + [一键整理] [恢复本容器默认] 两个小按钮；
- 交互（事件命中时 cancel 底层事件，**不会误拖物品**）：
  - 左键槽位：循环 自动→忽略→强制参与；
  - 右键槽位：复位为"自动"；
  - 左键按钮：一键整理 / 恢复默认分类；
  - 悬浮槽位：Tooltip 显示该槽分组名 + 当前手动状态（如"升级槽 · 精妙背包（手动:忽略）"）；
- 打开时每个"强制参与/忽略"覆写会**即时**体现在覆盖层颜色上。

### 5.2 一键整理

- 「整理当前容器」快捷键（默认 `O`）：对当前打开容器按当前设置的排序模式整理；
- 若光标持有物品/正在拖拽、菜单未打开或容器不可排序 → 不执行并 ActionBar 提示；
- 整理过程防抖（重复按不叠加任务）。

### 5.3 配置界面（Sorted 设置 Screen）

提供分类排序模式的配置：

- 排序模式：**仅合并**(默认) / 按名称 / 按注册名 / 按所属模组 / 按数量，支持升/降序；
- 范围：是否包含玩家主栏/快捷栏（默认包含）；
- 视觉：覆盖层颜色、透明度、默认开启与否；
- 预设列表：可单独禁用某模组预设；
- 性能：每 tick 操作上限、任务最长 tick 数；
- 安全：可选"整理上限封顶"（`0` = 不限制，仍以物品真实上限为准）。

### 5.4 快捷键（均为 `KeyConflictContext.GUI`，可在 Controls 中改绑/取消）

| 功能             | 默认键 | 说明                     |
| ---------------- | ------ | ------------------------ |
| 整理当前容器     | `O`    | 打开任意可排序容器时触发 |
| 槽位分类视图     | `P`    | 叠加层开/关              |
| 打开 Sorted 配置 | `K`    | 可在任意容器界面打开     |

## 6. 整理引擎（服务端执行）

对参与槽位集合运行两阶段，**全程以服务端权威为准**：

1. **合并阶段**：从左到右扫描参与槽位；对可容纳更多同键物品的槽位，把散落同键堆尽量并入；
   并入量为 `min(待并入数, 剩余可容)`（long 运算），每次并入前后都过槽位校验，失败即跳过该源槽；
   若一轮后仍有可并入项（少数"移来移去"场景）最多再重试固定次数后放弃，**保证终止**。
2. **排序阶段**（仅合并模式跳过）：按选定比较器生成"该放哪些槽"的放置序列，逐个把堆放到
   允许 `mayPlace` 的目标槽；容量很大时允许"一槽一种物"的天然归并（契合大堆叠玩法）。

引擎约束：

- 只操作"当前可参与"槽位；分类/覆写信息随 `SortRequestC2S` 一起发送（小体积 int 表），
  服务端用同一套分类器 + 覆写表最终定夺；
- 每次原子操作都尝试 `simulate=false` 前先校验；出现任何意外失败立即中止当前任务，
  保持已完成的增量并回 Acknowledge 说明；
- **取消条件**：菜单关闭/切换、光标开始持有物品、任务超过 tick 预算、容器指纹被第三方改变（如模组在整理中吞/加物品）；
- **防自激**：任务完成后对比指纹，若"整理前=整理后"则直接判定完成，不会因为外部模组的自动行为反复触发。

## 7. 需求 4：性能与安全设计

- **预算制**：排序以 `SortJob` 形式在服务端按 tick 切片（默认每 tick ≤ 128 次原子操作，可配），
  超大背包（几百上千槽）也不会单 tick 卡死；原子操作本身为内存级（无 IO）。
- **复杂度**：合并/排序基于槽位快照与桶（HashMap）线性/近线性；不做 O(n²) 的反复试移。
- **渲染开销**：覆盖层每帧仅画 ≤ 容器槽数 个矩形描边，仅在开启时执行；不拦截也不每帧重算分类。
- **网络**：请求包小、一次性；回执包小；失败静默恢复（客户端以服务端广播的槽位数据为准，不存在脏状态）。
- **数据安全兜底**：
  - 绝不写未经校验的槽位；服务端不信任客户端提供的"操作计划"，只信任其"忽略/参与意图"；
  - 护甲/副手/合成/结果/锁定/伪装槽在引擎层有硬保护，即使分类被误设也无法写入；
  - 所有改动走原版容器广播机制，关闭菜单/崩溃都不会遗留半截物品状态。
- **兼容其他整理工具**：默认不与其它整理模组抢默认键；用户若同时使用精妙背包自带排序，可把其菜单预设整组设为"忽略"。

## 9. 里程碑与验收（待审批后细化任务清单）

- **M1 脚手架**：Forge 1.20.1 工程 + mods.toml + 键位 + 网络通道跑通。
- **M2 引擎**：SortEngine + SortJob + 单测（含大堆叠 long 数学、防溢出、空槽容量动态化）。
- **M3 识别**：反编译锁定 Create:Storage / 精妙背包菜单结构 → 录入预设；启发式兜底 + 服务端硬保护验证。
- **M4 UI**：覆盖层渲染 + 槽位点击切换 + 配置界面 + 快捷键。
- **M5 打磨验收**：真实实例（Forge47.4.22 + Bigger Stacks + 上述模组）场景回归。

验收场景：

1. 普通箱子放多堆钻石/圆石 → 一键整理合并且按模式排序；**堆叠 1,073,741,823 级不报错不溢出**。
2. 精妙背包打开 → 升级槽红框（SPECIAL），整理后升级槽纹丝不动。
3. Create: Storage 储物盒/背包打开 → 过滤槽/升级槽默认不操作；覆盖层点选可改分类并即时生效。
4. 快速连按快捷键、整理中关菜单、整理中拿起物品 → 均安全中止、无错位。
5. 玩家物品栏（含护甲/副手/合成格）整理正确，护甲/副手/合成/结果不被碰。
6. 大背包（>500 槽）整理流畅无单帧卡顿（任务分片生效）。

## 10. 待确认决策（默认值见上，可在审批时一并调整）

1. **是否接受"两端都需安装"**（推荐，换取健壮性；纯客户端替代方案会引入 1.20.1 stateId 点击的不确定性）。
2. **一键整理默认范围**：容器主体 + 玩家主栏/快捷栏（推荐）还是仅容器主体。
3. **默认排序模式**：仅合并（推荐）——先求"不出错"，再叠加名称/模组等排序。
4. **覆盖层默认键位**：`P` 分类视图、`O` 整理、`K` 设置 是否可接受（全部可改绑）。
5. 大堆叠环境下是否希望**整理范围外的槽（UNKNOWN 灰色高亮）默认不参与**（当前默认：参与但高亮，可在配置改）。
